# CLAUDE.md — OPD Queueing System

Conventions reference for this codebase, compiled by reading every file in the
repo. This is a **small, single-purpose departmental queueing app** (a City
Health Office outpatient department queue), not a framework-driven project.
There is no build step, no package manager, and no test runner — treat that
as a real constraint, not an omission to "fix."

## 1. Stack

- **Language**: PHP, procedural style (no classes, no namespaces, no autoloading).
  `test_database.php` reports `PHP Version: 8.2.12` was used to generate the
  live DB dump, so target PHP 8.2 behavior, but the code itself avoids any
  8.x-only syntax and would run on much older PHP too.
- **Database**: MySQL/MariaDB via the **mysqli** extension (procedural-object
  style: `new mysqli(...)`, `$conn->query()`, `$conn->prepare()`). Never PDO.
  Dump header shows `Server version: 10.4.32-MariaDB` (i.e. XAMPP's bundled
  MariaDB).
- **Server**: Apache via XAMPP (`c:\xampp\htdocs\...`), no `.htaccess`,
  no routing layer — every `.php` file is a directly-hit entry point.
- **Frontend**: No framework, no bundler, no npm/composer. Plain HTML
  generated by inline PHP templates (`?>`/`<?php` mixing), vanilla
  `<script>` blocks (no modules), and hand-written CSS in `assets/`.
- **Package manager**: None. There is no `composer.json` or `package.json`.
  Do not introduce one without discussing it first — the whole point of this
  app is that it runs by copying the folder into `htdocs`.
- **Build tooling**: None. Files are served as-is by Apache.
- **Test runner**: None. `test_database.php` is not a PHPUnit test — it's a
  manually-run smoke-check script (`php test_database.php` from the CLI) that
  verifies the expected tables exist after running `database_setup.sql`.

There is no `/src`, no `/lib`, no `/views`, no `/public`. Every top-level
`.php` file is both the controller and the view for its own page — PHP logic
(POST handlers, queries) runs at the top of the file, HTML is emitted below
it in the same file. New pages should follow this same single-file pattern
unless you're explicitly asked to restructure.

## 3. Naming conventions

- **Files**: lowercase, `snake_case.php` (`clear_notify.php`, `queue_status.php`,
  `daily_reset.php`). No `index/controller/model` suffixing.
- **Routes**: there is no router — the "route" IS the filename
  (`doctor.php`, `admin.php`). Query params carry state, e.g.
  `admin.php?date=2026-05-01&period=week`, `doctor.php?doctor_name=...&table_number=...`.
- **DB tables**: lowercase `snake_case`, plural for log/fact tables singular
  for the core entity: `queue` (singular), `doctor_appointments_log`,
  `daily_statistics`, `historical_data` (all snake_case, no prefix like `tbl_`).
- **DB columns**: lowercase `snake_case` throughout — `queue_number`,
  `table_number`, `doctor_name`, `created_at`, `served_at`, `confirmed_at`,
  `log_time`, `last_updated`, `exported_to_csv`. Timestamps consistently end
  in `_at` except the log table's `log_time` and stats' `last_updated` —
  that inconsistency is original, not a typo to fix.
- **PHP variables**: `snake_case` (`$queue_number`, `$doctor_name`,
  `$table_number`), matching DB column names 1:1 wherever a variable maps to
  a column — keep doing this, it's the dominant pattern.
- **CSS classes**: `kebab-case`, BEM-ish but not strict BEM
  (`.queue-card`, `.queue-card.priority`, `.badge-priority`, `.stat-card`,
  `.kiosk-col.waiting-col`). State/variant classes are appended directly to
  the base class (`.queue-card.completed`, `.queue-card.cameback`), not as
  `queue-card--completed`.
- **CSS custom properties**: `--kebab-case` under `:root` (`--green-dark`,
  `--radius-lg`, `--shadow-md`). See §5 for the actual token values.

## 4. State management and data-fetching

There is no client-side framework and no SPA state. Every page is
server-rendered PHP; interactivity is vanilla JS layered on top:

- **Primary read pattern**: `mysqli::query()` with a hardcoded/interpolated
  SQL string for simple reads (`SELECT ... FROM queue WHERE status='waiting'`).
  **Prepared statements (`$conn->prepare()` + `bind_param`) are used only in
  `admin.php`**, which was written more carefully around the reports feature.
  Everywhere else (`index.php`, `doctor.php`) uses direct string interpolation
  of POST/GET values into SQL — see §9, this is a real (unfixed) SQL-injection
  surface, not a style choice to imitate for new code that handles user input.
- **Writes**: classic POST-redirect-GET. A form posts to the same file
  (`method="post"`, no `action` attr ⇒ posts to self), the handler at the top
  of the file does the write, then `header("Location: " . $_SERVER['PHP_SELF']); exit();`.
  Every POST handler that isn't an AJAX endpoint follows this exact
  three-line shape.
- **AJAX writes**: a few inline-edit forms (`update_queue_number`,
  `update_table_number` in `index.php`) detect
  `!empty($_SERVER['HTTP_X_REQUESTED_WITH'])` and branch to
  `header('Content-Type: application/json'); echo json_encode([...]); exit();`
  instead of redirecting. The client sets `headers: { 'X-Requested-With': 'XMLHttpRequest' }`
  on the `fetch()` call to trigger this branch. This is the only "API-like"
  pattern in the app — see §8.
- **Live updates / polling** (no websockets, no SSE):
  - `queue_status.php` returns `{waiting, serving, pending, last_update}` as
    JSON. Every page polls it (`fetch('queue_status.php')`) on a
    `setTimeout` loop (3000ms on index.php/display.php, 1000ms on doctor.php)
    and does `location.reload()` if the JSON string changed. This is a poor
    man's "has anything changed" check — it is NOT a diff, it just forces a
    full page reload.
  - `notify.json` is a flat file (not a DB table) used as a one-shot
    pub/sub channel for the "please proceed to table N" voice announcement.
    `doctor.php`'s `serve`/`notify` handlers write it via
    `file_put_contents('notify.json', json_encode([...]))`; `display.php`
    and `doctor.php` poll it every **50ms** via `fetch('notify.json?rand=...')`
    and speak it with `SpeechSynthesisUtterance`, then call
    `clear_notify.php` to reset it back to `'{}'`. The `?rand=` cache-buster
    is required because this is a static file fetch, not an endpoint with
    `Cache-Control` headers.
- No client-side caching, no localStorage/sessionStorage usage anywhere.

## 6. Display / board screens

Two competing kiosk implementations exist side by side, both loading
`assets/display.css`:

- **`display.php`** — the current one. 3-column layout (`waiting-col` /
  `serving-col` / `pending-col`), serving column splits into 4 fixed
  `.table-column` groups (Table 1–4, hardcoded — adding a 5th physical
  table requires editing this file's PHP array-bucketing logic directly,
  there's no config for table count). Stat row shows **"Served Today"**
  (scoped to `DATE(served_at) = CURDATE()`). Priority bucket collapses
  `'yes'` and `'infectious'` together into one shown card
  (`$row['priority'] === 'yes' || $row['priority'] === 'infectious'`).
- **`display_backgrounded.php`** — an older/alternate variant. Same
  structure but: stat row shows **"Total Served"** (all-time, no date
  filter), only checks `'yes'` for the priority bucket (does **not**
  special-case `'infectious'`), and has an inline `<style>` override
  widening `.serving-col`/`.waiting-col` flex ratios. Not linked from any
  nav — reachable only by hitting the URL directly. Treat `display.php` as
  the maintained one; if a display change is requested, ask whether
  `display_backgrounded.php` needs the same edit or is dead weight before
  touching it.

Both kiosk pages: fullscreen, `overflow: hidden` on `<html>/<body>` (no page
scroll, everything must fit viewport — hence the `vw`/`clamp()` sizing),
poll `notify.json` every 50ms for voice announcements and `queue_status.php`
every 3000ms for reload-on-change. Neither has any interactive
elements/forms — purely read-only.

## 7. Auth and session handling

**There is no authentication system.** Any user with network access to the
server can open `index.php` (operator), `doctor.php`, or `admin.php`
directly — there's no login page, no password, no role check, no
`$_SESSION['user_id']` guard anywhere. This app relies entirely on network
isolation (LAN-only deployment) for access control. Do not assume a
logged-in user exists when writing new code.

Session (`session_start()`) is used only as **lightweight form-state
memory**, not identity:
- `doctor.php` stashes `doctor_name`/`table_number` in `$_SESSION` so a
  doctor doesn't have to re-type their name/table on every page load;
  GET/POST values take precedence over session when present, falling back
  to session otherwise (`doctor.php:186-205`).
- `index.php` calls `session_unset()` immediately after `session_start()` on
  every load — it deliberately does NOT persist anything in session; this
  looks like leftover scaffolding rather than an intentional pattern, worth
  confirming with whoever owns this file before copying it elsewhere.

## 8. API conventions

There is no formal API layer / no REST resource design. What exists:

- **Page routes** (`index.php`, `doctor.php`, `admin.php`, `display.php`):
  return full HTML documents. State comes from POST body (write actions) or
  GET query string (read filters like `admin.php?date=&period=`). Redirect
  after every mutating POST via `header('Location: ' . $_SERVER['PHP_SELF'])`.
- **JSON endpoints** (`queue_status.php`, `clear_notify.php`, and the
  X-Requested-With branches inside `index.php`'s inline-edit handlers):
  - Always `header('Content-Type: application/json'); echo json_encode([...]);`.
  - **No envelope convention** — no `{success, data}` or `{status, error}`
    wrapper shape shared across endpoints. Each endpoint invents its own
    flat shape: `queue_status.php` → `{waiting, serving, pending, last_update}`;
    `clear_notify.php` → `{status: 'cleared'}`; the inline-edit AJAX handlers
    in `index.php` → `{error: ''}` or `{error: 'duplicate'|'invalid'}` (empty
    string means success, not a boolean flag — check for `data.error === ''`,
    as the existing JS client code does).
  - **No HTTP status codes are ever set for errors.** Every response is
    `200 OK` regardless of outcome; failure is only signaled inside the JSON
    body (or, in the worst case, an inline `echo` of a raw SQL error string
    — see §9). If you add a new JSON endpoint, match the existing flat,
    ad-hoc shape rather than inventing a `{success,data,error}` envelope —
    consistency with siblings matters more than "correctness" here, but flag
    it if asked to formalize this.
- No auth headers, no CSRF tokens, no rate limiting, no API versioning.

## 9. Things a new developer will trip over

1. **SQL injection is present and widespread, not hypothetical.** Most
   handlers in `index.php`/`doctor.php` build queries via direct string
   interpolation of `$_POST`/`$_GET` values
   (e.g. `index.php:14`: `"SELECT id FROM queue WHERE queue_number = $queue_number ..."`
   — `$queue_number` is cast `(int)` first so that one's safe by luck of the
   cast, but `doctor.php`'s `pending`/`cancel`/`transfer` handlers interpolate
   `$conn->real_escape_string($_POST['doctor_name'])` results directly into
   f-string-style queries, which is *escaping*, not parameterization).
   **`admin.php` is the one file that consistently uses prepared statements**
   (`$conn->prepare()` + `bind_param`). If you touch query-building code
   anywhere else, prefer converting to prepared statements rather than
   copying the interpolation pattern, even though interpolation is what's
   already there.
2. **The live schema and the checked-in `.sql` files have drifted.** Compare:
   - `queue.sql` (stale): `status ENUM('waiting','serving','served')`, no
     `priority`, no `confirmed_at`, no `pending`/`cancelled` statuses.
   - `opdqueue.sql` (a full phpMyAdmin dump, header dated **May 6, 2026** —
     the most recent artifact in the repo and the actual production schema):
     `queue.status` is `enum('waiting','serving','served','pending','cancelled')`
     and there's an additional `priority enum('no','yes','infectious','completed','came_back','follow_up')`
     column plus `confirmed_at datetime`.
   - `database_setup.sql` / `README_DATABASE_SETUP.md` describe
     `doctor_appointments_log.action` as
     `enum('served','pending','cancelled','notified')`, but the live dump
     (`opdqueue.sql:599`) has it as plain `varchar(50)` — and the code
     writes a 5th value, `'transferred'`, that was never in the original
     enum (`doctor.php:154`), which is presumably *why* it was loosened to
     varchar.
   - **Trust `opdqueue.sql`'s live `CREATE TABLE` statements (and by
     extension the columns actually read/written in the PHP) over
     `database_setup.sql`/`queue.sql`/the README when they disagree.**
     Those setup files look like initial scaffolding that was never updated
     as the schema evolved via ad-hoc `ALTER TABLE`s.
3. **`config.php` runs a migration on every single request.** It does
   `SHOW COLUMNS FROM queue LIKE 'confirmed_at'` and conditionally
   `ALTER TABLE` on every page load if the column is missing
   (`config.php:15-18`). This is how `confirmed_at` was rolled out. If you
   add a new column going forward, you either need to update
   `opdqueue.sql`/`database_setup.sql` by hand and document a manual
   migration step, or follow this same self-healing-migration pattern in
   `config.php` — there's no dedicated migrations folder/tool.
4. **`notify.json` is a world-writable flat file used as a message queue.**
   It lives at the web root (`c:\xampp\htdocs\...\notify.json`), is
   directly fetchable over HTTP (`fetch('notify.json?rand=...')`), and is
   overwritten via `file_put_contents()` from PHP with no locking. Under
   concurrent requests this can race, and because it's world-readable, any
   client on the LAN can read the "next call" payload before the intended
   kiosk does. This is intentional-enough infra for a single-clinic LAN app,
   but don't assume it's safe to reuse this pattern for anything sensitive.
5. **Two kiosk display pages, only one maintained** — see §6. Don't
   assume `display_backgrounded.php` is dead code to delete or a fork to
   ignore without asking; it's just undocumented which one is "current" for
   any given deployment.
6. **50ms and 1000ms polling loops** (`doctor.php`'s `pollNotify`,
   `display.php`'s `pollNotify`) hit `notify.json`/`queue_status.php`
   extremely frequently — this is deliberate for near-instant voice
   announcements, not a bug, but it means every open browser tab is
   hammering the server continuously. Keep this in mind before adding more
   pages with the same pattern, or before "optimizing" the interval down —
   the whole point of 50ms is the audio needs to fire almost immediately
   after a doctor clicks "Serve"/"Notify."
7. **`config.php` hardcodes credentials** (`root` / empty password / `opdqueue`
   db name) with a `// change as needed` comment — there's no `.env`, no
   environment-variable loading, no `config.local.php` gitignore split. Any
   environment-specific config change means editing `config.php` directly.
8. **`index.php` has an operator-facing "waiting queue" section that's
   effectively dead in normal flow**: the visible waiting list on the main
   page only shows a collapsed one-card-per-priority-bucket view (same
   dedup-by-priority pattern as the kiosk), and the *only* way to see the
   full waiting list is the "View Full List" button that opens a modal
   (`#waitingListModal`) — easy to miss when first reading the page.
9. **Inconsistent status/priority value casing and meaning overlap**:
   `priority` reuses the value `'completed'` to mean "requirements
   completed, waiting to be called" (NOT "queue entry completed" — that's
   what `status='served'` means). A patient can simultaneously have
   `status='waiting'` and `priority='completed'`. Read the whole
   `WHERE`/`ORDER BY` clause around any `priority`/`status` usage before
   assuming what a bucket means — the two columns are not orthogonal in the
   way their names suggest.
10. **No `.gitignore` observed** — `notify.json` (runtime state) and
    `report_month_2026_05.csv` (a generated report) are sitting in the repo
    tree alongside source files. Don't assume everything at the root is
    source-of-truth code; some of it is runtime/output state that happens
    to live next to the PHP files because the app has no separate data
    directory.
